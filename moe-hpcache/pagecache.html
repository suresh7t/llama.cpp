1. Executive Summary

GGBufMoE is a standalone C prototype for testing a database-style storage architecture for sparse MoE inference. Instead of allowing mmap() and the operating-system page cache to determine model residency, GGBufMoE explicitly manages model pages, expert-to-page mappings, asynchronous storage I/O, host residency, request coalescing, and LRU eviction.

The central hypothesis is not that 8 KiB is universally optimal. The hypothesis is that an inference runtime knows considerably more about model access semantics than a generic virtual-memory subsystem does. An application-controlled buffer manager can therefore make expert-aware decisions and overlap storage I/O with computation.

Core idea: treat immutable GGUF model data like a database treats immutable pages: maintain an application-owned directory/index, explicitly fetch pages asynchronously, retain hot pages in a controlled buffer pool, and use model execution knowledge to prefetch pages before they are needed.

2. Goals and Non-Goals

2.1 Goals

  • Build a small, understandable standalone C implementation.
  • Read model data directly from a GGUF file without using memory mapping for model-page residency.
  • Represent logical model data using 8 KiB pages.
  • Maintain an explicit page directory and LRU buffer pool.
  • Map (layer, expert, tensor) to file extents and logical pages.
  • Use asynchronous file I/O with multiple outstanding requests.
  • Coalesce adjacent logical pages into larger physical reads when useful.
  • Use single-flight behavior so concurrent requests for the same missing page share one I/O operation.
  • Measure cache behavior, I/O amplification, queue depth, latency, and prefetch effectiveness.
  • Create a clean integration boundary that could later be used by llama.cpp.

2.2 Non-goals for the first prototype

  • Replacing the llama.cpp tensor/GGML execution engine.
  • Implementing CUDA kernels.
  • Implementing a complete tokenizer.
  • Supporting writable model files or dirty-page writeback.
  • Assuming that every GGUF model has expert-contiguous storage.
  • Claiming that 8 KiB is the final production page size.

3. Model and Storage Model

GGUF provides an immutable file containing metadata, tensor descriptors, and tensor data. Tensor descriptors identify tensor names, dimensions, data types, and offsets. GGBufMoE treats those offsets as the physical address space from which logical pages are constructed.

GGUF file
+---------------------------------------------------------------+
| Header                                                        |
+---------------------------------------------------------------+
| Metadata KV                                                   |
| tokenizer / architecture / dimensions / etc.                 |
+---------------------------------------------------------------+
| Tensor descriptors                                            |
| name | shape | type | offset                                  |
+---------------------------------------------------------------+
| Tensor data                                                   |
|                                                               |
|   expert/layer tensor bytes ...                               |
|                                                               |
+---------------------------------------------------------------+

The prototype should first inspect the actual Qwen3.8 GGUF layout. The implementation must not assume that all tensors belonging to an expert are contiguous or that one expert occupies one fixed-size extent.

6. Index Design

6.1 Expert index

A token is not the correct cache key for expert weights. The router operates on the hidden state and selects experts at a particular layer. Therefore the natural identity is:

(layer, expert)

The tensor dimension is needed because one expert may consist of multiple tensors. A practical catalog representation is:

Expert
  layer
  expert_id
  tensor_count
  tensors[]

TensorExtent
  tensor_id
  file_offset
  byte_length
  first_page
  page_count

For 48 × 512 identities, a direct two-dimensional array is attractive:

expert_index[48][512]

The array itself is tiny. The larger objects are the extent lists referenced by each entry. This is analogous to a database index whose key lookup is cheap while the result points to a larger set of pages.

6.2 Page identity

A logical page is identified by a stable page ID. Conceptually:

page_id = logical model byte offset / 8192

For pages that cross tensor or alignment boundaries, the catalog can retain the exact file extent needed by the reader. The page ID should therefore be treated as a runtime buffer-manager identity rather than as a promise that every tensor begins on an 8 KiB boundary.

7. 8 KiB Logical Page Cache

The host cache is an explicit buffer pool containing fixed-size 8 KiB logical pages. Each slot contains the page bytes plus management metadata.

PageSlot
  page_id
  generation
  state
  pin_count
  last_use
  buffer[8192]

7.1 Page states

StateMeaning
EMPTYNo logical page assigned.
LOADINGAn asynchronous read is outstanding.
RESIDENTPage bytes are valid and available to readers.
EVICTINGSlot is being removed from active use.
FAILEDLast load failed; requesters receive an error.

7.2 Why separate logical and physical page sizes?

The logical cache page remains 8 KiB because it gives the prototype a simple, database-like unit of residency. Physical storage I/O does not have to be 8 KiB.

For example, eight adjacent logical pages can be serviced by one 64 KiB asynchronous read:

logical:  [P100][P101][P102][P103][P104][P105][P106][P107]
physical: [---------------------- 64 KiB --------------------]
                              one async read

The buffer manager can then install the individual 8 KiB pages into separate cache slots. This lets the experiment measure the tradeoff between fine-grained residency and larger, more efficient physical I/O.

8. Page Directory and LRU

The page directory answers:

page_id -> slot_id

A hash table is appropriate for a sparse page address space. The LRU structure is independent of the lookup structure:

Hash table:
    page_id -> slot

LRU:
    MRU <-> ... <-> LRU
              |
           eviction

This separation is intentional. The hash table provides fast identity lookup; the LRU provides replacement policy. Neither structure needs to contain the page bytes themselves.

8.1 Pinning

A page that is actively being consumed must not be selected for eviction. A simple reference count or pin count provides this protection:

pin_count > 0  => not evictable
pin_count == 0 => eligible for LRU eviction

9. Asynchronous I/O

The inference path should not perform synchronous file reads. On Windows, the initial backend should use overlapped file I/O, with an I/O completion mechanism such as IOCP. A later POSIX backend can use an appropriate asynchronous interface such as io_uring.

Request | v Page Directory ---- hit ----> RESIDENT page | miss | v Is page already LOADING? | yes | no v v attach waiter allocate slot | v submit async read | v completion queue | v mark RESIDENT | v wake all waiters

9.1 Single-flight requests

If several inference operations request the same page while it is being loaded, only one physical read should be issued. Additional requesters attach to the existing operation.

Bad:
    request A -> disk read P
    request B -> disk read P
    request C -> disk read P

Desired:
    request A ----+
    request B ----+--> one disk read P --> all complete
    request C ----+

9.2 Generation counters

A cache slot can be reused while an old asynchronous operation is completing. Every slot therefore receives a generation counter. Completion processing must validate (slot_id, generation, page_id) before installing data. This prevents a stale completion from overwriting a newer page assignment.

10. Request and Completion API

The first C interface should remain deliberately small:

gbm_handle *gbm_open(const char *path, const gbm_config *cfg);

int gbm_lookup_page(
    gbm_handle *h,
    uint64_t page_id,
    gbm_page_ref *out);

int gbm_prefetch(
    gbm_handle *h,
    const uint64_t *page_ids,
    size_t count);

int gbm_wait(
    gbm_handle *h,
    gbm_page_ref *ref);

void gbm_release(
    gbm_handle *h,
    gbm_page_ref *ref);

int gbm_close(gbm_handle *h);

The important semantic property is that gbm_lookup_page() may return a pending result rather than forcing a synchronous disk operation. Waiting occurs at an explicit synchronization boundary.

11. Prefetch Architecture

Sparse MoE execution provides unusually valuable information for prefetching. Once the router determines the expert IDs required by a layer, the runtime can translate:

(layer, expert)
      |
      v
expert index
      |
      v
tensor extents
      |
      v
logical page IDs
      |
      v
missing pages
      |
      v
async I/O queue

The desired sequence is:

router
  -> identify experts
  -> submit page requests
  -> perform/overlap I/O
  -> execute other available work
  -> consume expert weights

This is substantially different from generic OS paging: the application can know that a set of pages will be required before the corresponding matrix operation starts.

12. Host Cache and GPU Cache

The prototype initially concentrates on the host cache. The eventual inference path can have two independent residency domains:

                    Model storage
                         |
                    async disk I/O
                         |
                  +------+------+
                  |             |
              Host cache     GPU cache
                  |             |
                  +------->-----+
                     H2D transfer

A GPU page miss therefore has two possible outcomes:

  1. Host page hit: transfer the existing page to GPU memory.
  2. Host page miss: fetch from storage, install in host cache, then transfer.

This creates a useful two-level hierarchy without requiring the GPU cache and host cache to share the same replacement policy.

13. Tokenizer and Vocabulary Boundary

Tokenization is deliberately outside the MoE page cache. The model's vocabulary can be represented as a compact lookup structure:

UTF-8 input
    |
    v
tokenizer / merge logic
    |
    v
token ID
    |
    v
embedding / transformer
    |
    v
logits
    |
    v
selected token ID
    |
    v
ID -> token string

For the vocabulary, the natural reverse mapping is a direct array:

token_id -> {offset, length}
             |
             v
       token string blob

The forward tokenizer lookup can use a hash table or a radix/trie-like structure. The important architectural point is that token IDs do not identify experts. Expert selection occurs later from the router's computation over the hidden state.

14. GGUF Catalog Construction

The first executable should be a GGUF inspector rather than an inference engine. It should report:

  • GGUF version and metadata.
  • Tensor count.
  • Tensor names.
  • Tensor types.
  • Tensor dimensions.
  • Tensor file offsets and lengths.
  • Alignment.
  • Likely expert/layer naming patterns.
  • Contiguity relationships among expert tensors.

This inspection step is important because the page mapping must be derived from the actual file rather than from assumptions about the model's logical architecture.

16. C Data Structures

A deliberately plain C representation keeps the prototype easy to debug and makes the memory ownership rules visible.

typedef enum {
    GBM_PAGE_EMPTY,
    GBM_PAGE_LOADING,
    GBM_PAGE_RESIDENT,
    GBM_PAGE_EVICTING,
    GBM_PAGE_FAILED
} gbm_page_state;

typedef struct {
    uint64_t page_id;
    uint32_t slot_id;
    uint32_t generation;
    gbm_page_state state;
    uint32_t pin_count;
    uint64_t last_use;
} gbm_page_entry;

typedef struct {
    uint64_t file_offset;
    uint32_t length;
    uint32_t page_first;
    uint32_t page_count;
    uint32_t tensor_id;
} gbm_extent;

typedef struct {
    uint32_t layer;
    uint32_t expert_id;
    uint32_t extent_count;
    gbm_extent *extents;
} gbm_expert;

The exact structures can evolve after the first GGUF inspection. The prototype should avoid premature abstraction until the actual tensor layout is understood.

17. Physical Read Coalescing

The logical request queue may contain:

P100, P101, P102, P103, P104

If the corresponding file offsets are adjacent, the request manager can transform them into one physical operation:

P100..P104
      |
      v
one contiguous file range
      |
      v
one overlapped read
      |
      v
split completion into five logical pages

Coalescing should be configurable. The benchmark must be able to disable it so that its contribution can be measured independently.

18. Concurrency Model

The first implementation should establish clear ownership rather than maximize thread count. A practical model is:

  • Inference/request threads submit page requests.
  • A request manager protects page-directory state.
  • The asynchronous I/O backend owns outstanding file operations.
  • Completion processing transitions pages from LOADING to RESIDENT.
  • LRU manipulation occurs under controlled synchronization.

Because the model is read-only, there is no dirty-page or writeback protocol. That significantly simplifies correctness compared with a general-purpose database buffer manager.

The prototype should compare progressively more capable mechanisms rather than only comparing two endpoints.

19.1 Metrics

  • Logical page lookups.
  • Logical page hits.
  • Logical page misses.
  • Duplicate/single-flight misses.
  • Pages read.
  • Physical bytes read.
  • Logical bytes consumed.
  • Physical/logical I/O amplification.
  • Number of outstanding I/O operations.
  • Read latency distribution.
  • Cache occupancy.
  • Evictions per second.
  • Prefetch requests.
  • Useful prefetches.
  • Prefetch waste.
  • Time spent waiting for pages.
  • CPU cost per lookup.

19.2 Important derived metric

I/O amplification =
    physical bytes read
    -------------------
    logical bytes consumed

This metric is particularly important when comparing 8 KiB logical pages against larger coalesced physical reads.

20. Trace-Driven Testing

Before integrating with an inference engine, the buffer manager can consume a trace such as:

layer expert
0     17
0     92
0    301
1     17
1    144
...

The trace driver converts each expert identity into the corresponding page requests. This makes cache algorithms reproducible without requiring GPU execution.

Later, the trace can be captured from llama.cpp during actual Qwen3.8 inference and replayed against different cache sizes and policies.

21. Integration Path into llama.cpp

  1. Build and validate the GGUF catalog independently.
  2. Verify expert-to-tensor identification for Qwen3.8.
  3. Validate page offsets against direct file reads.
  4. Measure the standalone buffer manager using synthetic traces.
  5. Capture real expert access traces from llama.cpp.
  6. Replay real traces without changing inference execution.
  7. Add asynchronous page prefetch to the inference path.
  8. Replace selected mmap-backed expert accesses with GGBufMoE page references.
  9. Measure end-to-end token generation rate and page wait time.
Integration principle: GGBufMoE should first become a measurable storage/cache subsystem. It should not initially be entangled with CUDA kernels, scheduling, or model mathematics.

25. Open Questions

  1. Exact tensor layout: Are all expert tensors for a given layer physically contiguous?
  2. Physical I/O size: What read size gives the best SSD throughput without causing excessive read amplification?
  3. Logical page size: Is 8 KiB optimal, or should 4/8/16/32/64 KiB be benchmarked?
  4. Cache size: What host-cache capacity produces the useful working-set hit rate?
  5. Prefetch distance: How early can expert pages be submitted without wasting I/O?
  6. Cross-token locality: How stable are expert selections across adjacent tokens?
  7. Cross-layer locality: Can pages be retained effectively across layers?
  8. GPU interaction: Should GPU residency use the same page granularity or a different transfer unit?
  9. Compression/quantization: Does the tensor quantization format introduce useful natural I/O boundaries?

28. Success Criteria

The prototype is successful if it can demonstrate, with reproducible measurements, that explicit application-controlled paging can:

  • Correctly map Qwen3.8 expert requests to GGUF file ranges.
  • Maintain an explicit bounded host cache.
  • Issue multiple asynchronous storage operations.
  • Avoid duplicate reads for concurrent requests.
  • Coalesce adjacent logical pages when beneficial.
  • Prefetch pages using expert-selection information.
  • Produce detailed CSV performance traces.
  • Provide measurable page-hit and page-wait behavior that can be compared directly against the mmap baseline.

29. Design Principle

GGBufMoE should remain a small buffer manager, not become another inference framework. The clean separation is:

GGUF model
   |
   +-- immutable catalog
   |
   +-- expert index
   |
   +-- page manager
   |      |
   |      +-- hash directory
   |      +-- LRU buffer pool
   |      +-- async I/O
   |      +-- prefetch
   |
   +-- inference engine
          |
          +-- router supplies expert identities
          +-- GEMM consumes resident expert data

That separation allows each component to be measured independently and gives the project a credible path from a standalone C experiment to an eventual llama.cpp storage backend.
